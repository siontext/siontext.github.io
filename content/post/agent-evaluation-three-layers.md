# AI 에이전트 평가 — 답변·과정·운영 세 층으로 보기

---

> 💡 **한 줄 요약**: 에이전트는 최종 답 정확도 하나로 평가하지 않는다. **답변 품질, 과정 품질, 운영** 세 층으로 보고, 에이전트가 여럿이면 공통 지표에 유형별 핵심 지표를 하나씩 둔다. 프롬프트나 모델이 바뀌면 평가 세트 전체를 다시 돌린다.

> 📎 에이전트 개발 진척률에서 품질 검증 단계를 통과율로 재는 이야기는 [AI 에이전트 진척률, 어떻게 측정할까](/post/agent-progress-definition-of-done/)에서 다뤘다. 이 글은 그 통과율을 **무엇으로 채점하는지**를 다룬다.

---

## 정확도 95%면 잘 만든 에이전트일까

에이전트를 하나 만들어 테스트했더니 최종 답 정확도가 95%가 나왔다고 하자. 숫자만 보면 좋은데, 그 안에 이런 경우가 섞여 있을 수 있다.

- 중간에 엉뚱한 도구를 불렀는데 운 좋게 답은 맞았다
- 근거 문서에 없는 내용을 지어냈는데 문장이 자연스러워서 통과했다
- 답은 맞는데 한 번 답하는 데 30초가 걸리고 비용도 크다

챗봇은 보통 질문과 답 한 쌍을 비교해서 평가한다. 에이전트는 여러 단계를 거치며 도구를 부르고 다른 에이전트에게 일을 넘기니까, 이 방식으로는 위 문제가 안 보인다. RAGAS의 Faithfulness나 Answer Relevancy 같은 단일 응답 지표도 마지막 답만 보기 때문에 위험한 경로로 정답에 도착한 에이전트에게 만점을 준다.

---

## 세 층으로 본다

| 층 | 질문 | 지표 |
| --- | --- | --- |
| ① 답변 품질 | 무엇을 답했나 | 정답 일치, 충실성, 관련성, 안전성 |
| ② 과정 품질 | 어떻게 답했나 | 라우팅 정확도, 도구 호출 정확도, 과제 완료 |
| ③ 운영 | 얼마나 들었나 | 지연 시간, 토큰·API 비용, 오류율 |

### ① 답변 품질

최종 답을 본다.

| 지표 | 보는 것 |
| --- | --- |
| Answer Correctness (정답 일치) | 준비한 정답과 맞는가 |
| Faithfulness (충실성) | 검색 문서나 도구 결과에 없는 말을 지어내지 않았는가. 환각 여부 |
| Answer Relevancy (관련성) | 묻는 말에 맞는 답인가 |
| Safety (안전성) | 개인정보, 금지 표현, 유해 내용을 내지 않았는가 |

### ② 과정 품질

답에 이르는 경로(trace)를 본다.

| 지표 | 보는 것 |
| --- | --- |
| Routing Accuracy (라우팅 정확도) | 질문 의도를 맞게 읽고 맞는 에이전트나 흐름으로 보냈는가 |
| Tool Call Accuracy (도구 호출 정확도) | 맞는 도구를 맞는 인자로, 맞는 순서로 불렀는가 |
| Task Completion (과제 완료) | 과제를 끝까지 마쳤는가 |

도구 호출 정확도는 기대한 호출 목록과 실제 호출을 비교하면 되니까 판정용 LLM 없이도 계산할 수 있다. 과제 완료도 상태가 구조화돼 있으면 "실행 후 DB 상태가 기대한 상태와 같은가"처럼 정해진 답으로 비교할 수 있다. τ-bench가 이 방식을 쓴다.

### ③ 운영

지연 시간, 토큰·API 비용, 오류율(타임아웃, 도구 실패, 예외)을 본다. 품질이 같다면 이 수치가 좋은 쪽을 고른다.

---

## 에이전트가 여럿이면: 공통 지표 + 핵심 지표 하나

역할이 나뉜 에이전트가 여러 개면 지표를 전부 재기 어렵다. 충실성과 안전성은 모든 에이전트에 공통으로 적용하고, 유형마다 "이게 틀리면 그 에이전트는 실패"인 지표를 하나씩 핵심으로 둔다.

| 에이전트 유형 | 핵심 지표 | 판정 방법 |
| --- | --- | --- |
| 계산형 (이자·수수료 계산 등) | 정답 값 일치 | 숫자 자동 비교 |
| 추천형 (상품·문서 추천) | 정답 항목 포함 여부 | 목록 자동 비교 |
| 연결형 (다른 에이전트·흐름으로 넘김) | 라우팅 일치 | 기대 목적지와 자동 비교 |
| 분류형 (의도·카테고리 분류) | 분류 정확도 | 라벨 자동 비교 |
| 질의응답형 (서술형 답변) | LLM 채점 점수 | 기준표(rubric)로 LLM-as-a-Judge |

공통 지표로는 에이전트끼리 비교하고, 핵심 지표로는 어느 에이전트가 왜 나빠졌는지 찾는다.

---

## 누가 판정하나

| 판정 주체 | 언제 쓰나 |
| --- | --- |
| 자동 비교 | 정답이 숫자, 라벨, 목록처럼 명확할 때 |
| LLM-as-a-Judge | 서술형처럼 정답을 하나로 정하기 어려운 답을 많이 채점할 때 |
| 사람 | 돈, 법, 안전이 걸린 중요한 건 |

LLM-as-a-Judge는 사람 대신 LLM이 기준표를 보고 점수를 매기는 방법이다. 기준표를 분명하게 쓰고, 점수와 함께 이유도 내게 한다.

LLM 판정을 배포 기준으로 쓰려면 사람이 매긴 판정과 얼마나 일치하는지 먼저 확인(calibration)해야 한다. LLM 판정이 통과시킨 환각을 사람 검토자가 잡아낸 사례도 보고돼 있다. 보통 대량 채점은 LLM에 맡기고, 애매한 경계 사례는 사람이 본다.

---

## 바뀔 때마다 다시 돌린다: 회귀 평가

프롬프트 한 줄이나 모델 버전 하나만 바뀌어도 다른 질문의 답이 달라질 수 있다. 그래서 바뀔 때마다 평가 세트 전체를 다시 돌려 이전 결과와 비교하는데, 이걸 회귀 평가(Regression Evaluation)라고 한다.

```text
[프롬프트·모델 변경] → [평가 세트 전체 재실행] → [이전 결과와 비교] → 나빠지지 않았으면 배포
```

비교 기준은 골든 데이터셋(정답이 붙은 질문 모음)이고, 결과가 이전보다 나빠지지 않았을 때만 배포한다. 운영 중에도 같은 지표를 실제 요청 일부에 적용하면 품질이 떨어지는 걸 일찍 알 수 있다.

---

## 정리: 챗봇 평가와 에이전트 평가

| 항목 | 챗봇 단일 응답 평가 | 에이전트 평가 |
| --- | --- | --- |
| 보는 범위 | 질문 → 답변 한 쌍 | 질문 → 라우팅 → 도구 호출 → 답변 전체 경로 |
| 대표 지표 | 정답 일치, 충실성, 관련성 | 위 지표 + 라우팅, 도구 호출, 과제 완료 |
| 판정 | 정답 비교, LLM-as-a-Judge | 자동 비교 + LLM-as-a-Judge + 사람 |
| 운영 지표 | 지연 정도 | 지연, 비용, 오류율 |
| 놓치는 것 | 과정 오류, 위험한 경로 | 과정까지 보므로 이 둘을 잡는다 |

---

> ✅ **기억할 것**: 에이전트 평가는 답변 품질, 과정 품질, 운영 세 층으로 본다. 에이전트가 여럿이면 충실성·안전성을 공통으로 두고 유형별 핵심 지표를 하나씩 더한다. 정답이 명확하면 자동 비교, 서술형은 LLM-as-a-Judge, 중요한 건은 사람이 판정하고, 프롬프트나 모델이 바뀌면 전체를 다시 돌린다.
