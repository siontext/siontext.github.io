# LLM이 답변 규칙을 지키게 하려면 — 뉴로 심볼릭으로 검사하고 고치기

---

> 💡 **한 줄 요약**: 규칙을 프롬프트에 알려 주는 것만으로는 LLM이 다 지키지 못한다. 그래서 LLM이 쓴 답변을 코드가 규칙 사전으로 검사하고, 걸린 문장만 LLM이 한 번 고치게 한 뒤, 뜻이 바뀌지 않았는지 코드가 다시 확인하는 구조를 설계했다. 판단은 LLM이, 정답이 있는 확인은 코드가 맡는 **뉴로 심볼릭** 방식이다.

> 📎 문제를 정리하고 방법을 설계해 제안한 단계의 기록이다. 구현과 측정은 아직 하지 않았다.

---

## 문제: 규칙을 알려 줘도 다 지키지 못한다

고객 응대 에이전트의 답변은 회사의 UX 라이팅 가이드도 지켜야 한다. 가이드에는 말투, 용어, 표기 규칙이 잔뜩 들어 있다.

- 어려운 한자어는 쉬운 말로 쓴다 (익일 → 다음 날)
- 유의사항은 정중하게 하십시오체로, 나머지는 친근한 해요체로 쓴다
- 메뉴 경로는 `메뉴 > 하위 메뉴`처럼 꺾쇠 앞뒤를 띄운다

권장 용어만 수백 개가 되기도 한다. 이걸 프롬프트에 넣고 "지켜라"라고 해도 LLM은 일부를 빠뜨린다. IFScale 벤치마크에서는 지시가 500개일 때 가장 좋은 모델도 약 68%만 지켰다.

정리해 보니 문제는 일곱 가지였고, 세 묶음으로 나뉜다.

| 묶음 | 문제 |
| --- | --- |
| 규칙 지키기 | ① 규칙이 많아 빠뜨린다 |
| | ② 가이드가 원칙과 예시뿐이라 목록 밖 단어는 판단이 필요하다 |
| | ③ 문장마다 말투가 달라야 한다 (유의사항은 하십시오체) |
| 고칠 때 | ④ 고치다가 뜻이 바뀐다 ("받을 수 없습니다" → "어려울 수 있습니다") |
| | ⑤ 글자로만 찾으면 엉뚱한 단어가 걸린다 ("본 서비스 → 이 서비스" 규칙으로 '본'을 찾으면 "본인"까지 걸림) |
| 확인하기 | ⑥ 톤(해결 방법을 알려 줬는가)은 코드로 확인할 수 없다 |
| | ⑦ 잘 지켰는지 잴 기준이 없다 |

④는 특히 위험하다. "받을 수 없습니다"가 "어려울 수 있습니다"로 바뀌면 고객은 받을 수도 있다고 읽는다.

## 해결 방향: 뉴로 심볼릭

LLM과 코드는 잘하는 일이 다르다.

| | 뉴로 (LLM) | 심볼릭 (규칙·코드) |
| --- | --- | --- |
| 맡는 일 | 판단이 필요한 일 | 정답이 정해진 일 |
| 잘하는 것 | 문맥을 읽고 판단하고 고쳐 쓴다 | 빠짐없이 확인하고 근거를 댈 수 있다 |
| 약한 것 | 규칙 수백 개를 빠짐없이 지키지 못한다 | 적혀 있지 않은 건 못 찾는다 |
| 예 | 이 문장이 유의사항인가? | 익일 → 다음 날 |

![규칙을 프롬프트에 넣기만 하는 방식과 검사를 통과해야 나가는 방식 비교](/img/posts/llm-ux-writing/weak-vs-strong.png)

둘을 섞어 쓰는 방식을 뉴로 심볼릭(Neuro-symbolic)이라고 한다. 이번 설계에서는 규칙을 LLM이 참고하는 데서 끝내지 않고, 코드 검사를 통과한 답변만 내보낸다.

## 설계: 네 단계

![네 단계와 예시 문장이 바뀌는 과정](/img/posts/llm-ux-writing/process-example.png)

### ① 쓰기: 문장마다 상황 꼬리표를 붙인다

에이전트가 답변을 쓸 때 문장 묶음마다 상황 꼬리표를 같이 붙이게 한다. 꼬리표는 고객 화면에는 나가지 않는다.

| 꼬리표 | 알리는 문장 |
| --- | --- |
| 안내 (정보 전달, 다음 단계 안내) | 해요체 |
| 상세설명 (상품 설명, 가입 절차) | 해요체 |
| 유의사항 (약관, 법적 고지, 위험 안내) | 하십시오체 |
| 마케팅 (혜택 소개, 가입 권유) | 해요체 |

"이 문장이 유의사항인가"는 판단이 필요한 일이라 LLM이 맡는다. 답변을 쓰는 김에 같이 붙이니까 상황 판단을 위해 LLM을 따로 부르지 않아도 된다.

### ② 검사: 코드가 규칙 사전과 대조한다

| 검사 | 보는 것 | 예 |
| --- | --- | --- |
| 용어 | 쓰지 말아야 할 단어가 있나 | 익일 → 다음 날 |
| 어미 | 문장 끝이 꼬리표에 맞나 | [유의사항]인데 "-돼요"로 끝남 |
| 표기 | 정해진 모양을 지켰나 | 메뉴>하위메뉴 → 메뉴 > 하위메뉴 |

용어 검사에서 문제 ⑤가 생긴다. '본'을 글자로만 찾으면 "본인", "기본"까지 걸린다. 그래서 POS-aware Matching을 쓴다. 형태소 분석기로 품사까지 확인해서, 관형사 '본'(본 서비스)만 걸고 명사의 일부인 '본'(본인)은 넘긴다.

![글자로만 찾기와 품사까지 보기 비교](/img/posts/llm-ux-writing/pos-matching.svg)

규칙 사전은 가이드의 규칙을 옮겨 적은 표다. 몇백 줄 규모라 CSV 파일로 코드와 함께 두고 git으로 관리한다. DB나 별도 서버는 필요 없다.

### ③ 고치기: 걸린 문장만, 한 번만

LLM에게는 걸린 문장과 지적 내용만 준다.

| LLM에게 주는 것 | 예 |
| --- | --- |
| 걸린 문장 | "익일에 지급돼요." |
| 지적 (규칙) | 익일 → 다음 날 |

걸리지 않은 문장은 손대지 않는다. 단어 하나 바꾸는 일도 LLM에게 맡기는 이유는 조사 때문이다. "익일에"를 "다음 날에"로 바꾸는 건 쉽지만, 단어에 따라 조사가 달라지는 경우(을/를, 이/가)가 있어서 문장을 자연스럽게 맞추려면 LLM이 낫다.

고치기는 한 번만 한다. 반복할수록 나아지는 폭은 줄고, 뜻이 바뀔 가능성은 커진다.

### ④ 확인: 뜻이 바뀌지 않았는지 코드가 본다

| 확인 | 막는 예 |
| --- | --- |
| 규칙 재검사 | ② 검사와 같은 기준 |
| 숫자가 같은가 | 연 3.5% → 연 5.3% |
| 된다/안 된다가 같은가 | 받을 수 없습니다 → 받기 어려울 수 있어요 |

하나라도 걸리면 고치기 전 원래 글을 내보낸다(Fallback). 규칙을 조금 어긴 글이 뜻이 바뀐 글보다 낫다고 봤다. LLM 호출은 걸린 문장이 있을 때만 한 번 늘어난다.

네 단계를 주고받는 순서로 그리면 이렇다.

## 코드로 못 보는 톤은 오프라인으로 평가한다

"안 되는 이유와 다음 행동을 알려 줬는가" 같은 톤은 코드로 확인할 수 없다(문제 ⑥). 이건 실시간으로 막지 않고, 실제 답변을 모아 따로 채점한다.

| 방법 | 내용 |
| --- | --- |
| LLM-as-a-Judge | LLM이 채점자가 된다 |
| Checklist Evaluation | 점수 하나 대신 예/아니오 질문으로 쪼개서 채점한다. "안 되는 이유를 알려 줬는가?" |
| 사람 정답과 비교 | UX 담당자가 매긴 정답과 맞는지 먼저 확인한 뒤 쓴다 |
| Cross-family Judge | 답변을 쓴 모델과 다른 회사 모델로 채점한다 |

자주 걸리는 문제는 에이전트 프롬프트나 규칙 사전에 반영한다.

## 왜 이렇게 했나: 근거

| 설계 결정 | 근거 |
| --- | --- |
| 규칙은 프롬프트가 아니라 코드로 검사 | 지시 500개에서 최고 모델도 약 68%만 지킴 (IFScale) |
| | 단어 바꾸기 규칙은 약 37개를 넘으면 95% 이상 지키지 못함 (GPT-4o mini, Instruction Capacity) |
| 지금 필요한 규칙만 나눠서 주기 | 정책을 단계별로 나눠 주면 작은 모델(GPT-4o-mini)이 큰 모델(GPT-4o)보다 정책을 잘 지킴 (JourneyBench) |
| 고치기는 한 번만 | 반복해서 고칠수록 개선 폭이 줄어듦 (Self-Refine) |
| 고친 뒤 뜻을 코드로 비교 | 다시 쓰기에서 최대 75%의 출력이 확실성 표현을 바꿈. 의료 분야 예시에서 1번 고치면 20%, 5번이면 40% (Certainty Distortion) |
| 톤은 예/아니오로 쪼개서 채점 | 체크리스트로 쪼개면 판정 모델 간 일치도가 오름 (CheckEval) |

## 한계와 남은 것

| 과제 | 상태 | 남은 일 |
| --- | --- | --- |
| 적용: 상황에 맞는 규칙 고르기 | 방향 정함 (꼬리표) | 꼬리표가 맞게 붙는지 실제 답변으로 재기 |
| 강제: 규칙을 어기지 못하게 | 방법 정함 (검사 → 고치기 → 확인) | 뜻 비교가 잘 되는지 예문으로 시험 |
| 평가: 잘 지켰는지 재기 | 방법 정함 (규칙별 위반율 + Checklist) | 사람 정답 데이터 만들기 |
| 평가 기준: 무엇을 통과로 볼지 | 미정 | 현재 위반율(Baseline)을 잰 뒤 목표치 결정 |

설계하면서 받아들인 한계도 있다.

- 톤은 실시간으로 막지 못한다. 오프라인 평가로 찾아서 고친다.
- 확인 단계는 숫자와 된다/안 된다만 본다. '반드시', '~수 있다' 같은 확실성 표현의 변화는 평가에서 자주 보이면 검사에 추가한다.
- 걸린 문장이 있으면 LLM 호출이 한 번 늘어 그만큼 느려진다.
- 검사를 통과해야 내보내니 글자 단위 스트리밍은 할 수 없다. 문장마다 검사해 내보내는 Sentence-level Buffering으로 기다리는 시간을 줄일 수 있는데, 얼마나 빨라지는지는 직접 재 보고 정할 생각이다.

![다 쓴 뒤 한 번에 검사하는 방식과 문장마다 검사해 내보내는 방식 비교](/img/posts/llm-ux-writing/streaming.png)

---

> ✅ **기억할 것**: 규칙이 많으면 LLM은 빠뜨린다. 정답이 있는 규칙(용어·어미·표기)은 코드가 검사하고, 걸린 문장만 LLM이 한 번 고치고, 뜻이 바뀌었는지는 다시 코드가 본다. 코드로 못 보는 톤은 실시간으로 막지 말고 오프라인에서 Checklist로 채점한다.
